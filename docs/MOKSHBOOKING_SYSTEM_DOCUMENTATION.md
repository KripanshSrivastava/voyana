## 1. Executive summary

MokshBooking is a travel-lead marketplace built on Next.js 16 (App Router, React 19, Turbopack). It serves three distinct audiences from one codebase:

1. **Public visitors** browse destinations/packages and submit enquiries.
2. **Vendor travel agents** purchase distributed leads using pre-paid Lead Credits.
3. **Platform admins** curate the CMS, manage vendor onboarding, moderate content, and configure business rules.

Leads flow in from four channels (website, Google Lead Forms, Meta Lead Ads, partner API) into a single ingestion pipeline. Each qualified lead can be sold to at most 2 agents (shared) or to 1 agent exclusively — enforced atomically at the Postgres level in a single Prisma transaction. Revenue is denominated in **Lead Credits** (integer units purchased by agents through a manual QR-based approval flow); a legacy Razorpay INR wallet remains for backward compatibility.

Supabase Auth owns credentials; the application layer adds email verification and optional 2FA gates. Vercel hosts the runtime. Upstash Redis + Next's `unstable_cache` sit in front of the Postgres read path for public content. Resend delivers every transactional email through one verified domain, category-branched local-parts.

## 3. Application architecture

- **Routing:** Next.js App Router. Three route groups: `(home)` (landing), `(site)` (public marketing), plus explicit `admin/(panel)` and `agent/(portal)` protected areas.
- **Rendering:** Public pages are static (ISR, 5-minute revalidate for content, 1-hour for static marketing). Authenticated pages are dynamic per-request.
- **Data access:** Prisma client is a singleton via [lib/db.ts](../lib/db.ts) with `withReadRetry` wrapping public reads.
- **Auth session:** Supabase auth cookie; refreshed on every request via [proxy.ts](../proxy.ts) → `updateSession`. Session-to-app-user mapping via `authId` (Supabase UUID) with email fallback + self-heal.
- **Authorization:** Layer 1 = `requireRole(...roles)` in every API route; Layer 2 = `requireArea(session, area)` for admin sub-role gating; Layer 3 = business-rule checks inside Prisma transactions (purchase.ts, credits.ts).
- **Caching:** two-tier — Next `unstable_cache` per-instance + Upstash Redis cross-instance. Only ever caches public content and site settings. Never caches wallet, purchase state, or authorization data.

## 17. Lead management architecture

- **Ingestion:** [lib/leads/ingest.ts](../lib/leads/ingest.ts) — single entry point for every source.
- **Scoring:** [lib/leads/scoring.ts](../lib/leads/scoring.ts) — assigns `quality` + `qualityScore` from phone/email presence, dates, budget, requirements, source.
- **Deduplication:** in-window (default 72h from `leadExpiryHours`) match on same phone + destinationText → flag as duplicate, link `duplicateOfId`, never delete.
- **Idempotency:** webhook replays deduped via `Lead @@unique([source, externalId])`.
- **Code generation:** [lib/leads/code.ts](../lib/leads/code.ts) generates `LD-YYYY-######` with 4-attempt retry.
- **Alerts:** [lib/leads/alerts.ts](../lib/leads/alerts.ts) — fanned out via `Promise.allSettled`; in-app notifications bulk-inserted with `notifyMany`.
- **Auto-buy:** [lib/leads/autobuy.ts](../lib/leads/autobuy.ts) — **sequential** by design to re-check capacity between purchases; only SHARED, only DOMESTIC/INBOUND, only APPROVED+VERIFIED agents with enough credits.

Full flow diagram: [ARCHITECTURE.md § 2](ARCHITECTURE.md#2-lead-lifecycle).

## 18. Lead lifecycle

Statuses on `Lead`:
```
NEW → CONTACTED → QUALIFIED → AVAILABLE → SHARED → IN_PROGRESS → CONVERTED
                                      ↓
                                    LOST | INVALID | DUPLICATE
```

Statuses on `LeadAssignment`:
```
PURCHASED → CONTACTED → INTERESTED → QUOTE_SENT → NEGOTIATING → BOOKED → WON | LOST | NO_RESPONSE | SPAM
```

Transitions are enforced in code (`ASSIGNMENT_STATUS_TRANSITIONS` in [lib/constants.ts](../lib/constants.ts)), not at the DB layer.

## 19. Lead purchase architecture

Full sequence: [ARCHITECTURE.md § 3](ARCHITECTURE.md#3-lead-purchase-transaction-shared--exclusive).

**Atomicity guarantees** (all inside a single `prisma.$transaction`):

1. **Slot claim is race-safe** — `updateMany` with `assignmentCount { lt: maxAgents }`. If two agents click Buy Shared simultaneously and only one slot remains, only one increment succeeds. The loser sees `count === 0` and gets a 409.
2. **Insufficient-credits detection is race-safe** — `AgentCreditBalance.updateMany` with `balance { gte: credits }`. No TOCTOU: if the balance drops between initial check and debit, the guarded `updateMany` returns count=0.
3. **Exclusive → all-slots-consumed** — exclusive purchase increments by `(maxAgents - assignmentCount)`, ensuring no shared sale is possible after.
4. **INTERNATIONAL locked to exclusive** — Server rejects SHARED at the transaction level, not just the UI.
5. **Same agent can't double-buy** — enforced by `LeadAssignment @@unique([leadId, agentId])` + explicit tx check.

**Prices are always server-computed** via `computeLeadCharge()` from the lead's `tripCategory` + `SiteSetting` + `purchaseType`. Client-sent price fields are never trusted.

**Side effects (best-effort, never fail the purchase):** audit log, in-app notification, purchase-receipt email.

## 20. Wallet & payment architecture

**Two systems in one codebase:**

1. **Lead Credits (primary, active):** integer credits, purchased via manual QR flow (`LeadCreditPurchase` → admin approval), balance tracked in `AgentCreditBalance`, mutations via [lib/credits.ts](../lib/credits.ts) with `LeadCreditLedger` as append-only audit trail.
2. **INR Wallet (legacy, retained):** rupee balance in `AgentWallet`, mutations via [lib/wallet.ts](../lib/wallet.ts) with `WalletTransaction` audit trail. Still used by admin wallet-adjust and Razorpay top-up webhook. 🟡

**Manual QR flow (primary):**
```
Agent /agent/wallet
  → picks a LeadCreditPackage
  → POST /api/agent/credits/order (LeadCreditPurchase PENDING_REVIEW + MKB-YYYYMMDD-###### code)
  → agent uploads QR screenshot + transaction ref
Admin /admin/credit-orders
  → reviews the screenshot
  → POST /api/admin/credit-orders/[id]/approve
    → addCreditsInTx(type=CREDIT_PURCHASE) inside prisma.$transaction
    → Also writes a WalletTopup(status=PAID) row for legacy reporting compatibility
    → sends receipt email
```

**Legacy Razorpay:**
- `POST /api/agent/wallet/topup` creates a Razorpay order + `WalletTopup(status=CREATED)`.
- `POST /api/payments/razorpay/webhook` verifies HMAC signature against `RAZORPAY_WEBHOOK_SECRET`, marks PAID, credits wallet/credits. Idempotent on `WalletTopup.orderId`.

## 21. Authentication & authorization

**Session storage:** Supabase auth cookies (managed by `@supabase/ssr`, refreshed on every non-static request via [proxy.ts](../proxy.ts)).

**Session-to-user mapping:** `getSession` in [lib/auth.ts](../lib/auth.ts) — looks up `User.authId === auth.users.id`, falls back to email match and self-heals `authId` for legacy rows.

**Extra gates (app-level, layered on top of Supabase):**
- Email verification: `User.emailVerified` — set on OTP redemption
- Optional 2FA: `User.twoFactorEnabled` — issues `VerificationToken(TWO_FA)` on login, agent must clear before entering portal

**Guard layers:**

| Layer | Function | Where used |
|---|---|---|
| Session refresh | `updateSession` | `proxy.ts` middleware — every request |
| Session load | `getSession()` cached per-request | Server components + route handlers |
| Role guard (API) | `requireRole("AGENT"\|"ADMIN")` | Every `/api/**` route |
| Role guard (page) | `requireAgent()` / `requireAdmin()` in `lib/guards.ts` | Every protected layout |
| Sub-role guard | `requireArea(session, area)` | Admin routes with sub-role restrictions |
| Business rule | Inside Prisma transactions | Purchase, credits, spam refunds |

## 27. Business workflows

Each workflow below maps to a real code path.

### Customer submits enquiry
```
Landing hero search bar
  → user fills Destination + Date + Nights + Travelers
  → clicks Get Quote
  → LeadPopupModal opens pre-filled with hero values
  → user adds name + phone + email + city
  → POST /api/leads
    → Zod validation → ingestLead()
      → duplicate check (72h window)
      → scoreLead(): quality + qualityScore
      → Lead.create + LeadStatusHistory(NEW, SYSTEM)
      → parallel side effects (email customer + admin, alerts fanout, integration log, audit)
      → sequential autobuy for matching agents
  → success page + trackLeadConversion()
```

### Agent purchases a lead
See [ARCHITECTURE.md § 3](ARCHITECTURE.md#3-lead-purchase-transaction-shared--exclusive) and § 19 above.

### Agent reports spam
```
Agent /agent/leads/[id]
  → owns the lead (assignment exists)
  → picks reason + optional notes
  → POST /api/agent/leads/[id]/spam
    → SpamReport.create(status=PENDING) — unique[leadId, agentId]
    → audit
Admin /admin/spam-reports
  → PATCH /api/admin/spam-reports/[id]
    → approve: pick resolution=refund (auto: creditsBack) or credit or none
      → if refund: creditsBack via addCreditsInTx(CREDIT_REFUND)
      → record refundedAt, refundAmount, refundWalletTransactionId
      → mark assignment.status = SPAM
    → reject: SpamReport(status=REJECTED)
    → audit + notify agent
```

### Agent marks lead booked
```
Agent /agent/leads/[id]
  → LeadStatusControl → transition PURCHASED → CONTACTED → NEGOTIATING → BOOKED
  → POST /api/agent/leads/[id]/status
    → validate transition against ASSIGNMENT_STATUS_TRANSITIONS
    → LeadAssignment update + LeadAssignmentStatusHistory
    → if BOOKED, capture bookedValue + bookedAt (client passes these)
```

### Auto-buy pipeline
```
Any new priced lead → runAutoBuyForLead(leadId)
  → skip if lead is INTERNATIONAL (exclusive-only, agent must click)
  → find AgentPreference where autoBuyEnabled=true
  → for each pref, sequentially:
    → re-check lead capacity (may have been filled by earlier autobuy)
    → gate: agent.status=APPROVED, verificationStatus=VERIFIED, autoBuyCriteria matches lead, ≥1 credit
    → dedupe: skip if this agent already holds this lead
    → purchaseLead(actor=AGENT, purchaseType=SHARED) — same atomic transaction as manual
    → best-effort: notify + agentAutoLeadPurchased email + audit
```
See [lib/leads/autobuy.ts](../lib/leads/autobuy.ts).

### Lead alerts
```
Any new lead → runLeadAlerts(leadId)
  → find AgentPreference where alertInApp=true OR alertEmail=true
  → skip SUSPENDED / REJECTED agents
  → apply leadMatches(lead, alertCriteria(pref))
  → build inApp[] + emails[]
  → Promise.allSettled([notifyMany(inApp), ...emails])
```

### Password reset
```
User /agent/forgot-password
  → POST /api/auth/forgot-password { email }
  → silently issues VerificationToken(PASSWORD_RESET) with 32-byte hex if email exists
  → sends passwordResetEmail via account@
User clicks link → /agent/reset-password?token=…
  → inspectResetToken(): valid/expired/used check
  → user enters new password
  → POST /api/auth/reset-password { token, newPassword }
  → redeemPasswordReset(): mark consumedAt FIRST, then supabase.auth.admin.updateUserById
```

### Payment (manual credit purchase)
```
Agent /agent/wallet
  → picks LeadCreditPackage → POST /api/agent/credits/order
  → LeadCreditPurchase(status=PENDING_REVIEW, orderId=MKB-YYYYMMDD-######)
Agent uploads QR screenshot + txn reference (via BuyCreditsManual UI)
Admin /admin/credit-orders
  → reviews screenshot
  → POST /api/admin/credit-orders/[id]/approve
    → prisma.$transaction:
      → LeadCreditPurchase(status=APPROVED, reviewedAt/reviewedById/paidAt)
      → addCreditsInTx(agentId, credits, CREDIT_PURCHASE, "Package X")
      → creates a WalletTopup(status=PAID) linked back (legacy compat)
    → notify agent + walletCredited email
```

### Support ticket
```
Agent /agent/support (⏸ supportEnabled)
  → POST /api/agent/support { subject, category, body }
  → SupportTicket.create(status=OPEN) + SupportMessage.create(authorType=AGENT)
  → supportTicketCreated email
Admin /admin/support/[id]
  → PATCH /api/admin/support/[id] { status?, adminReply? }
  → append SupportMessage(authorType=ADMIN) + optional internal note
  → supportTicketReply email to agent if reply is non-internal
Agent /agent/support/[id]
  → POST /api/support/[id]/reply
```

## 28. Error & failure flows

### Invalid credentials
```
POST /api/auth/login
  → supabase.auth.signInWithPassword failure
  → response 401 { ok:false, error:"Login failed" }
UI shows inline error, no lockout logic implemented (⚠️ consider rate limiting)
```

### Race lost during purchase
```
Two agents click Buy Shared on a lead with 1 slot remaining
  → both hit purchaseLead()
  → both open transactions
  → both hit updateMany({ assignmentCount < maxAgents }) at nearly the same time
  → first commits; second sees count=0
  → second throws PurchaseError("This lead is fully distributed.", 409)
  → UI catches error, calls router.refresh() → grid re-fetches → card now shows "Sold out"
```

### Insufficient credits at debit time (race)
```
Agent has 1 credit, is auto-buying multiple leads in the same tick
  → first purchase debits successfully via updateMany balance≥1
  → second purchase: initial check passes if reads a stale balance, but tx debit's updateMany sees balance=0
  → count=0 → throw INSUFFICIENT_CREDITS → PurchaseError 402
  → autobuy loop's try/catch swallows it and moves on
```

### Duplicate webhook (Google Lead Forms replay)
```
POST /api/leads/google with same lead_id + source=google
  → Lead @@unique([source, externalId]) → INSERT fails / findFirst returns existing
  → ingestLead returns { alreadyExisted: true }
  → logIntegration(status=DUPLICATE)
  → 200 with existing lead's id/code
```

### Email delivery failure
```
sendEmail returns { ok:false } (Resend HTTP error)
  → caller's Promise.allSettled catches it
  → logIntegration(email, FAILED, message)
  → API response still succeeds — email is best-effort
Exception: admin invite. If Resend fails there, the invite is rolled back
  (Supabase auth user + User row deleted) so admin can safely retry.
```

### Duplicate lead in ingestion
```
72h window match on same phone + destinationText
  → NOT deduped: still creates a new Lead
  → sets Lead.isDuplicate = true and Lead.duplicateOfId = originalId
  → admin sees "DUP" tag on the leads list; agent-side surface is unaffected
```

### Supabase session missing on admin invite link
```
Invited admin clicks link too late (Supabase link expired)
  → /admin/set-password loads
  → SetPasswordCard reads supabase.auth.getUser() → returns "Auth session missing!"
  → UI renders "Invite link expired" card asking for a fresh invite
```

## 30. Security architecture

### Implemented ✅
- **Auth via Supabase** — credentials + password hashing outside our codebase.
- **Prisma parameterized queries** — SQL injection avoided by ORM.
- **Server-computed prices** — `computeLeadCharge()` server-side; no client price trust.
- **Atomic wallet + slot claims** — `updateMany` guards prevent TOCTOU on balance and capacity.
- **Webhook HMAC verification** — Meta (X-Hub-Signature-256), Razorpay (X-Razorpay-Signature). See `verifyMetaSignature` in [/api/leads/meta](../app/api/leads/meta/route.ts).
- **API-key + shared-secret gates** — Google Lead Forms + Partner API.
- **CSRF via Supabase cookie strategy** — auth token is HttpOnly per Supabase defaults.
- **Zod input validation** — all API bodies validated.
- **Password reset token hashing** — 32-byte raw token, sha256 stored.
- **OTP hashing** — email verification + 2FA codes stored as sha256, never plaintext.
- **Enumeration-safe forgot password** — always returns same response.
- **No PII pre-purchase** — marketplace list query has narrow `select` that excludes phone/email/customerName from unbought leads.
- **Admin invite via Supabase generateLink** — no plaintext password ever in email.
- **Audit trail** — `AuditLog` captures every sensitive action.
- **Sub-role RBAC** — 7 admin sub-roles with area-based gating.

### Partially implemented 🟡
- **Rate limiting** — none for login, forgot-password, OTP verify, or webhooks. ⚠️ recommended.
- **Session revocation on password change** — password change endpoint updates Supabase but does not force sign-out of other tabs (⚠️ verify against Supabase default behavior).
- **CSP / security headers** — no `next.config` header block. Only Next defaults.
- **Content moderation** — vendor submissions require admin approval, but no automated abuse checks.

### Missing / recommended 🚧
- **Rate limiting** on auth + webhook + public endpoints. Would fit naturally on top of Upstash Redis.
- **Login attempt throttling / account lockout.** No lockout on repeated failed attempts.
- **Refresh-token rotation** review — relies on Supabase defaults, not audited here.
- **Anti-automation on `/api/leads`** (public form). No CAPTCHA/honeypot present.
- **Supabase RLS policies** — service-role key bypasses everything, and all app queries go through Prisma. RLS not asserted here; if the DB is ever accessed via anon key from another surface, RLS becomes the sole line of defense. ⚠️ verify with the Supabase project.
- **Prisma query logging** disabled — no default `log: ["query"]` in prisma.ts. Turning it on in dev would help future performance work.
- **Bundle analyzer** wiring not present.

## 36. Technical risks

**Critical**

3. No login lockout — repeated failures don't slow down the caller.
4. `autoBuyEnabled` flag potentially not respected in ingest post-hook (verify).

**Medium**
6. Legacy Razorpay path retained but unclear if actively used — dead code risk if not maintained.

**Low**
